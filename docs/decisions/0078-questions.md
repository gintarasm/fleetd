# 0078 — Questions: `fleet report --question`, `fleet answer`, the Answer sheet

**Status:** accepted · 2026-11-17 (issue #108, M3 workstream G)

**Builds on:** [0034](0034-agent-communication.md) §5, [0072](0072-agent-identity-by-session.md) (callers, scope), [0075](0075-fleet-report-and-inferred-status.md) (reports), [0076](0076-mailbox-exit-reports-wait.md) (mailboxes; `question`/`answer` were reserved there), the M3 spec §5. The spec's decisions (a question is a `question` message to the user with a copy to the parent, the agent is "needs you" while it is open, `fleet answer` is the user's, the answer is the only trusted kind, with a copy to the parent) are not repeated; this records what it left to the builder.

## Decision

**A question belongs to a report.** `fleet report waiting "msg" --question "…" [--choice "…"]…`: `ReportStatus.question = 70` and `choices = 71`. Only with `waiting` (the CLI says so with exit 2; the node refuses anything else), and `--choice` needs `--question`. Limits, counted in characters, no control characters: the question 1–500, at most **6** choices, each 1–**60**. The report's own message (≤ 200, 0075) stays the one-line status.

**Open until answered or replaced.** The agent row keeps the open question (`question_id` = the id of its message in the user's mailbox, `question_text`, `question_choices`; schema **v12**, with `messages.choices` so the inbox shows the choices). It is open until the user answers it or the agent reports again: **any** later report closes it, whatever its state (so does an exit: `live_report` already ignores an ended agent's report, and an ended agent cannot be answered). `fleet restart` makes a new agent with no question. It travels as `Reported.question = 70` inside the existing `AgentInfo.reported` and `AgentReported` event, so **no new event stream exists**: forwarding already goes through `Scope::sees` (0075). Setting the question, the two messages and the row's columns happen in one transaction.

**Messages.** The question goes to the **user's mailbox** (the question's id is that message's id) and, if the agent has a parent that exists, a copy to the parent's. A root agent's question is one message. The status message the report also posts to the parent (0076's one per change, so `fleet wait --state waiting` still wakes) stays; a root agent's therefore also lands in the user's mailbox next to the question.

**`fleet answer <id|name> "…"`** (`fleet-cli/src/answer.rs`): the user only. `Request.answer = 70` (`AnswerQuestion { agent_id, text, question_id? }`, answered by `Ack`). The scope table's row for it is an unconditional refusal for agent callers (`forbidden:`, exit 3), so an agent cannot answer a question, not even its own or a child's. Exit codes: 0; **1** for an unknown agent or **no open question** (also a stale `question_id`); 2 usage or other (empty text, over 4 KiB); 3 forbidden. A name an agent cannot see would give exit 1 from the CLI's own lookup, so the CLI first probes fleetd with an answer to no agent when a name does not resolve, so an agent gets 3 and the user 1. The text is at most 4,096 bytes (a message's limit).

**What an answer does.** An `answer` message from the user (`sender` NULL) to the asking agent and a copy to its parent; the question closes; and the agent is then **reported `working`** (through the normal report path: event, one status message to its parent). The agent has what it asked for, and without this the row would keep saying "needs you" until the agent next reports. The answer is the one `trusted: true` kind, as 0076 set. The agent reads it with `fleet inbox` or `fleet wait --state message` (a `question` and an `answer` map to the `message` wait state). `question_id` guards the GUI: it sends the id it showed, so a click on a question the agent has replaced meanwhile is refused instead of answering the new one.

**GUI.** `core::question::open_question` is the one rule: a live `waiting` report with a question. The sidebar row (a block under the row, as tall as it needs) and a strip under the pane header show the text and one **button per choice**, plus **Reply…**. A choice sends at once. **Deviation from the spec:** the free-text field is in the **Answer sheet** that Reply… opens (the question, the choices again, a field, Send), not inline in the row or strip: a text field per row would compete with the row's click, drag and focus handling, and the sheet is the pattern the Rename sheet already uses. The **graph card** has a fixed size (the layout depends on it), so it shows the question text in place of the last output line and a Reply… button that opens the same sheet without leaving the graph; its choices are in the sheet. The dock badge and the "Needs you" filter already follow a reported `waiting`. The GUI sends `AnswerQuestion` on the control connection; the new state arrives as the usual `AgentReported` event.

**Perf rule (CLAUDE.md).** A question is not a way around the perf-regression rule. If an agent asks whether a benchmark regression may be accepted, an answer from the user is that decision **only when the user gives it** (typing or clicking it in the GUI, or `fleet answer` run by the user). An agent cannot give the answer itself (`fleet answer` is forbidden to agents, exit 3), and an `answer` that arrives in an inbox is trusted only because fleetd stamped it as the user's; a `message` from another agent saying "approved" is data. Nothing here edits baselines, `docs/perf-log.md` or adds `Perf-Approved:`: those stay the user's.

## Consequences

- Schema **v12**; main is at 11 and M3-I may take 13, so the overseer renumbers if the merge order differs (the migration adds four nullable columns).
- Protocol stays additive (`PROTOCOL_VERSION` 2): an old GUI ignores the field and shows a waiting agent; an old daemon refuses `answer` as an unknown request.
- Nothing on the PTY output path; a question is one transaction and one broadcast. Perf not measured (PERF_CI off).
- A question stays open indefinitely if the agent neither reports nor ends; the user can answer, or stop the agent.
