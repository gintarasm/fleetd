# 0018 — M1 protocol server and node

**Status:** accepted · 2026-11-13

## Protocol

**Context:** 0006 fixes protobuf messages, length-prefixed framing, binary output frames and a version handshake; 0005 puts the terminal grid on the node so reattach costs O(screen). M1 makes these concrete for the local unix socket (`<state-dir>/fleetd.sock`).

**Decision:**

- **Wire format** (`fleet-proto`, `FrameCodec`): every frame is `[u32 BE len][u8 kind][payload]`, `len` counting the kind byte and payload; a zero length, an unknown kind or `len > MAX_FRAME` (16 MiB) is a protocol error. Kinds: `1 Hello`, `2 HelloOk`, `3 HandshakeReject`, `4 Request`, `5 Response`, `6 Event` (protobuf payloads, package `fleet.v1`) and `7 Output`, whose payload is `[u64 BE agent_id][raw PTY bytes]`, deliberately not protobuf so terminal output is never re-encoded.
- **Handshake:** the client's first frame must be `Hello` (at most 4 KiB, within 5 s). `PROTOCOL_VERSION = 1`; a mismatch is answered with `HandshakeReject { reason }` and the connection is closed, otherwise `HelloOk`. At most 64 concurrent connections; more are rejected the same way.
- **Requests:** `Request { id, kind }` (`SpawnAgent`, `ListAgents`, `Attach`, `Detach`, `SendInput`, `Resize`, `KillAgent`) are answered strictly in order by `Response { id, kind }` (`AgentInfo`, `AgentList`, `AttachOk`, `Ack`, `Error`). `Response.id = 0` is reserved for unsolicited notices (today only `Error "lagged: re-attach"`). `Event::AgentExited` is pushed to every connection; for an attached agent it comes after the agent's last `Output`.
- **Terminal sizes:** `SpawnAgent` and `Resize` sizes must have each side in 1..=1000 and at most 250 000 cells (`MAX_DIM`, `MAX_CELLS`), else the response is an `Error`; in `SpawnAgent` a zero side means the default 80x24.
- **Attach:** `AttachOk { snapshot, cols, rows }` is queued before any `Output` of the new subscription, and the stream continues exactly where the snapshot ends (snapshot and subscription are taken under the lock that feeds the grid). Re-attaching replaces the previous subscription; attaching an exited agent yields its final screen and its exit event.
- **Exited agents are released:** on exit the node flushes and closes the agent's scrollback file, drops its PTY and grid, and keeps only the final snapshot bytes of the last 64 exits (`RETAINED_EXITED`, oldest evicted first), so a long-running daemon's fds and memory do not grow with the number of agents it has run. Attaching to an evicted exited agent (or one that exited under a previous daemon) yields `AttachOk` with an empty snapshot and size 0x0, followed by its exit event; it still lists from the store, and its history remains in its scrollback file. Killing an exited agent is a no-op; input and resize are errors.
- **Snapshot as ANSI:** the snapshot is a byte sequence that redraws the visible screen into a fresh terminal of the same size: `\x1b[?1049h` if the alt screen is active, then `\x1b[0m\x1b[H\x1b[2J`, the grid (text, SGR attributes incl. 256/truecolor and underline colour, wide and combining characters), the active pen, the non-default modes (cursor visibility, application cursor/keypad, mouse reporting 1000/1002/1003/1005/1006, focus events, alternate scroll, bracketed paste, autowrap, origin, insert, LNM) and a final CUP; a pending autowrap is recreated by re-emitting the last glyph. A pending synchronized update (`?2026`) is applied first, and an escape sequence or UTF-8 character split across reads (up to 4 KiB) is appended, so the client's parser continues in step. Clients need only a VT parser, no grid format. Known limits: the primary screen behind an active alt screen is not carried (blank until the app redraws after `?1049l`); not carried either are the scroll region (DECSTBM; alacritty exposes no accessor, so the client starts with a full-screen region), the saved cursor (DECSC), charsets, tab stops, the kitty keyboard mode stack, hyperlinks and soft-wrap markers.
- **Subscriber drop policy:** each subscription is a bounded channel of 256 output chunks (`SUBSCRIBER_CAPACITY`) that the PTY reader thread only `try_send`s into, so a slow client never slows its agent or other clients. A subscriber whose channel is full is dropped; the connection sends `Response { id: 0, Error "lagged: re-attach" }`, and the agent's exit event is then delivered through the connection's exit-event stream. The client must re-attach (the snapshot makes this cheap). Each connection has one writer fed by a 256-frame queue; a client that stops reading stalls only its own forwarders, which then lag out. The lag notice does not name the agent (a known gap; see Consequences).
- **Terminal query replies** (DSR/CPR, DA, …) are answered by the node's grid and written back to the agent only while no client is attached; while one is, the client's terminal answers. Replies are written without blocking and dropped if the agent's input is full.
- **Scrollback ring:** each agent's raw output is appended to `<state-dir>/scrollback/<id>.ring`, a fixed-size file (8 MiB of data plus a 16-byte header `[u64 LE write_pos][u64 LE total_written]`, mode 0600). Appends are buffered (64 KiB) and flushed without fsync; history is best effort, the live grid stays authoritative. M1 records it; serving it to clients comes later.
- **fd budget:** a running agent holds three fds in `fleetd` (the PTY master, one duplicate of it shared by the reader thread and input/reply writes, and its scrollback file); an exited one holds none. `fleetd`'s `main` raises the soft `RLIMIT_NOFILE` to the hard limit (at most `OPEN_MAX` = 10240 on macOS), so ≥ 50 agents fit even under a 256-fd soft and hard limit.
- **Agent states:** `running`, `exited` (with exit code) and `lost`: on startup the node marks every agent still `running` in the store (left behind by a crashed or killed daemon) as `lost`, since its PTY cannot be recovered (no handoff, 0013).
- **Schema compilation:** `fleet-proto/build.rs` compiles `proto/fleet.proto` with `protox` (pure-Rust protobuf compiler) and generates types with `prost-build`, so building needs no `protoc` on the machine or in CI.

**Consequences:** a reattach costs one screen (a 120x40 snapshot is typically well under 64 KiB; a screen full of distinct truecolor attributes can exceed it) regardless of output volume. A client attached to many agents at full throughput can be dropped as lagged even if it keeps up, because the daemon's forwarders compete for CPU with the agents' parsing (seen in the `daemon_flood50` benchmark); since the notice does not carry the agent id, such a client cannot re-attach selectively. Adding the agent id to the notice (a protocol change) is the follow-up. Benchmarks for the new hot paths: `daemon_flood50_*`, `reattach_snapshot_ns`, `frame_decode_output_64x64k_instructions`, `terminal_feed_64k_instructions`, `snapshot_120x40_instructions` (`bench/README.md`).

## Known limits / follow-ups

- **Passthrough limits of `fleet attach`.** The client's terminal sees the agent's output unfiltered, so: an agent that enables the kitty keyboard protocol (CSI-u, `CSI > flags u`) makes the terminal encode Ctrl-\\ as an escape sequence instead of byte 0x1c, and the detach key stops working until the agent pops the mode; an agent that leaves the alternate screen itself (`?1049l`) drops the client out of the alt screen `fleet attach` entered, so its output lands in the client's normal scrollback. On exit `fleet attach` soft-resets, pops one kitty keyboard level (`CSI < u`), leaves the alt screen and resets cursor visibility, bracketed paste, mouse (1000/1002/1003/1005/1006/1015), focus events (1004), application cursor keys and autowrap. Filtering these sequences is a follow-up.
- **Lag notice lacks the agent id.** `Response { id: 0, Error "lagged: re-attach" }` does not say which subscription was dropped, so a client attached to several agents cannot re-attach selectively. Follow-up: carry the agent id in the notice (protocol change, bump or extend `fleet.v1`).
- **Daemon CPU under a 50-agent flood.** In `daemon_flood50` (50 agents x 8 MiB, one client attached to all) `fleetd` uses ~380% CPU and drops 45–48 of 50 subscriptions as lagged although the client keeps up (~10% CPU): the agents' parsing threads starve the connection's forwarders. Tracked by `daemon_flood50_lagged_subscriptions` (report-only); the first M2-prep perf target.

## Daemon shutdown

**Context:** v1 has no PTY handoff to a successor daemon (0013). Leaving agents behind when `fleetd` stops would orphan untracked processes, the stale-session leak 0013 exists to prevent.

**Decision:** Stopping `fleetd` (SIGTERM/SIGINT/SIGHUP) terminates its agents: SIGTERM to each agent's process group, up to 2 s grace, then SIGKILL (and a short wait). Exits are recorded through the normal exit path, so their rows become `exited`. An agent that still has not reported, or every agent after a daemon crash, stays `running` in the store and is marked `lost` on the next start.

**Consequences:** Upgrading or restarting the daemon ends all agents (drain-and-restart, as 0013 v1 requires); shutdown takes at most ~2.5 s. Agents that escape their process group (new session) are not reached.
